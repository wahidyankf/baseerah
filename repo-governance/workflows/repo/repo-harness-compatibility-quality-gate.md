# Repository Harness Compatibility Quality Gate Workflow

**Purpose**: Periodically (on-demand) verify that the repo's platform-binding catalog and
committed binding files still match each supported coding-agent harness's **current upstream
configuration conventions**, and fix any drift.

**IMPORTANT — Scope Clarification (External Drift vs. Internal Consistency)**:

This workflow addresses **external drift** — divergence caused by upstream harness vendors
changing their configuration conventions after the binding files were last authored. It is the
external-drift counterpart to the deterministic, agent-free pre-push parity guard
(`rhino-cli agents validate-bindings`), which checks **internal consistency** (e.g., that the
secondary binding directory stays in sync with the primary binding directory as generated by the
sync script). Do NOT
confuse the two: the pre-push guard runs automatically and requires no human involvement; this
workflow is an on-demand research-and-fix cycle that tracks upstream harness evolution.

**What this workflow validates**:

- **Platform-binding catalog** (`docs/reference/platform-bindings.md`) — does it still
  accurately describe each harness's current root instruction file, dotdir layout, and
  mechanical translation rules?
- **Committed binding files** — do the committed binding files conform to each harness's
  current configuration conventions (frontmatter fields, file locations, permission schemas,
  model identifiers, tool capability declarations, etc.)?

**When to use**:

- After a supported harness publishes a breaking configuration change (e.g., new required
  frontmatter field, deprecated dotdir path, changed model identifier format)
- Periodically as a scheduled hygiene audit (recommended: before major releases)
- When adding support for a new harness (run after initial binding files are committed)
- When the platform-bindings catalog has not been reviewed in an extended period

## Execution Mode

**Preferred Mode**: Agent Delegation — invoke `repo-harness-compatibility-checker` and
`repo-harness-compatibility-fixer` via the Agent tool with `subagent_type`
(see [Workflow Execution Modes Convention](../meta/execution-modes.md)).

**Fallback Mode**: Manual Orchestration — execute workflow logic directly using
Read/Write/Edit tools when Agent Delegation is unavailable.

The Agent tool runs delegated agents that persist file changes to the actual filesystem,
making it the preferred approach when these agents exist as defined delegated agent types.

**How to Execute**:

```
User: "Run repo harness compatibility quality gate workflow in strict mode"
```

The orchestrator will:

1. Invoke `repo-harness-compatibility-checker` via the Agent tool (delegates per-harness
   research to `web-research-maker`, diffs upstream conventions against local files, writes
   drift audit report)
2. Invoke `repo-harness-compatibility-fixer` via the Agent tool (reads audit, applies fixes
   to catalog and binding files, writes fix report)
3. Iterate until zero drift findings achieved on two consecutive validations
4. Show git status with modified files
5. Wait for user commit approval

**Fallback (Manual Mode)**:

```
User: "Run repo harness compatibility quality gate workflow in manual mode"
```

The orchestrator executes checker and fixer logic directly using Read/Write/Edit tools in
the main context — use this when agent delegation is unavailable.

## Research Delegation

The checker delegates **multi-page per-harness research** to `web-research-maker` rather
than performing web lookups inline. This keeps the audit context lean and lets the checker
focus on diffing and reporting.

For each supported harness, the checker spawns a `web-research-maker` sub-task that:

- Fetches current authoritative upstream documentation (official docs site, changelog,
  migration guides)
- Extracts the harness's current configuration conventions (frontmatter schema, file
  locations, model identifier format, permission schema, tool declarations)
- Returns a structured summary that the checker compares against the local catalog entry
  and committed binding files

The checker cites the upstream source URL and retrieval date in the audit report so reviewers
can verify research independently.

## Steps

### 1. Initial Validation (Sequential)

Run the harness compatibility check to identify all drift findings.

**Agent**: `repo-harness-compatibility-checker`

- **Args**: `mode: {input.mode}`
- **Output**: `{audit-report-1}` — Initial audit report in
  `generated-reports/repo-harness-compatibility__{uuid}__{timestamp}__audit.md`

**What the checker does**:

For each harness listed in the platform-binding catalog:

1. Delegates research to `web-research-maker` (fetches current upstream conventions)
2. Compares upstream conventions against the local catalog entry in
   `docs/reference/platform-bindings.md`
3. Compares upstream conventions against the committed binding files for that harness
4. Records any drift as a finding (CRITICAL / HIGH / MEDIUM / LOW)

**Finding categories** (not exhaustive — checker may add harness-specific categories):

- **CRITICAL**: Required field removed from harness schema; existing binding files use a
  path the harness no longer reads; breaking frontmatter change
- **HIGH**: New required field not present in binding files; model identifier format changed
- **MEDIUM**: Deprecated field still in use; catalog description inaccurate but non-breaking
- **LOW**: Style/formatting drift; new optional field available but not yet adopted

**Success criteria**: Checker completes and generates audit report.

**On failure**: Terminate workflow with status `fail`.

### 2. Check for Findings (Sequential)

Analyze audit report to determine if fixes are needed.

**Condition Check**: Count findings based on mode level in `{audit-report-1}`:

- **lax**: Count CRITICAL only
- **normal**: Count CRITICAL + HIGH
- **strict**: Count CRITICAL + HIGH + MEDIUM
- **ocd**: Count all levels (CRITICAL, HIGH, MEDIUM, LOW)

**Below-threshold findings**: Report in audit but do not block success.

**Decision**:

- If threshold-level findings > 0: Proceed to step 3 (reset `consecutive_zero_count` to 0)
- If threshold-level findings = 0: Initialize `consecutive_zero_count` to 1 (this check is
  the first zero), proceed to step 4 for confirmation re-check (consecutive pass requirement)

**Depends on**: Step 1 completion

### 3. Apply Fixes (Sequential, Conditional)

Apply validated fixes from the audit report based on mode level.

**Agent**: `repo-harness-compatibility-fixer`

- **Args**: `report: {audit-report-N}, mode: {input.mode}`
- **Output**: `{fix-report-N}` — Fix report listing what was updated and what was flagged
  for human resolution
- **Condition**: Threshold-level findings exist from step 2
- **Depends on**: Step 2 completion

**Auto-fixable scope**:

- Catalog entry updates in `docs/reference/platform-bindings.md` (description corrections,
  updated field names, new harness entries)
- Mechanical binding file updates (frontmatter field additions/renames, file relocations
  within the dotdir, permission schema updates where the new schema is unambiguous)

**Out-of-scope** (fixer flags and exits — orchestrator surfaces to human):

- Fixes requiring product-level decisions (e.g., adopting a new harness capability that
  changes agent behavior, removing a binding entirely)
- Fixes where the upstream change is ambiguous or has multiple migration paths

**Fix scope based on mode**:

- **lax**: Fix CRITICAL only (skip HIGH/MEDIUM/LOW)
- **normal**: Fix CRITICAL + HIGH (skip MEDIUM/LOW)
- **strict**: Fix CRITICAL + HIGH + MEDIUM (skip LOW)
- **ocd**: Fix all levels (CRITICAL, HIGH, MEDIUM, LOW)

**Success criteria**: Fixer successfully applies all threshold-level auto-fixable findings.

**On failure**: Log errors, proceed to step 4 for verification.

### 4. Re-validate (Sequential)

Re-run the harness compatibility check to confirm fixes resolved findings without
introducing new ones.

**Agent**: `repo-harness-compatibility-checker`

- **Args**: `mode: {input.mode}`
- **Output**: `{audit-report-N+1}` — Verification audit report
- **Depends on**: Step 3 completion (or step 2 when findings were zero)

**Note on research reuse**: For harnesses where the upstream conventions did not change
between iterations (i.e., the fixer only made local file edits), the checker may reuse the
prior `web-research-maker` research summary rather than re-fetching. The checker logs
whether research was reused or refreshed for each harness.

**Success criteria**: Checker completes validation.

**On failure**: Terminate workflow with status `fail`.

### 5. Iteration Control (Sequential)

Determine whether to continue fixing or terminate.

**Logic**:

- Count findings based on mode level in `{audit-report-N+1}` (same as Step 2)
- Track `consecutive_zero_count` across iterations (resets to 0 when threshold-level
  findings > 0, increments when = 0)
- If `consecutive_zero_count` >= 2: Proceed to step 6 (double-zero confirmed)
- If `consecutive_zero_count` < 2 AND threshold-level findings = 0: Loop back to step 4
  (confirmation check — no fix needed, just re-verify)
- If threshold-level findings > 0 AND iterations >= max-iterations: Proceed to step 6
  (Partial)
- If threshold-level findings > 0 AND iterations < max-iterations: Loop back to step 3
- If iteration count reaches 5: Emit escalation warning to user-visible output (matches
  the convergence safeguard pattern used across repo quality-gate workflows)

**Below-threshold findings**: Continue to be reported in audit but do not affect iteration
logic.

**Depends on**: Step 4 completion

**Notes**:

- Default behavior: runs up to 7 iterations (default max-iterations)
- Consecutive pass requirement: zero findings must be confirmed by a second independent
  check before declaring success
- Each iteration uses the latest audit report

### 6. Finalization (Sequential)

Report final status and summary.

**Output**: `{final-status}`, `{iterations-completed}`, `{final-report}`

**Status determination**:

- **Success** (`pass`): Zero threshold-level findings on two consecutive validations
- **Partial** (`partial`): Findings remain after max-iterations, or fixer flagged
  out-of-scope findings requiring human resolution
- **Failure** (`fail`): Technical errors during check or fix

**Depends on**: Reaching this step from step 2, 4, or 5

## Termination Criteria

**Success** (`pass`):

- **lax**: Zero CRITICAL findings on 2 consecutive checks (HIGH/MEDIUM/LOW may exist)
- **normal**: Zero CRITICAL/HIGH findings on 2 consecutive checks (MEDIUM/LOW may exist)
- **strict**: Zero CRITICAL/HIGH/MEDIUM findings on 2 consecutive checks (LOW may exist)
- **ocd**: Zero findings at all levels on 2 consecutive checks

**Partial** (`partial`):

- Threshold-level findings remain after max-iterations safety limit
- Fixer reported out-of-scope findings that require human resolution

**Failure** (`fail`):

- Technical errors during check or fix (e.g., `web-research-maker` unreachable, binding
  file unreadable)

**Note**: Below-threshold findings are reported in the final audit but do not prevent
success status. Success requires two consecutive zero-finding validations (consecutive pass
requirement).

## Example Usage

### Standard Invocation (Strict Mode)

```
User: "Run repo harness compatibility quality gate workflow in strict mode"
```

The orchestrator invokes specialized agents via the Agent tool:

- Validate each harness entry against upstream conventions
  (`repo-harness-compatibility-checker` delegated agent)
- Apply fixes for CRITICAL/HIGH/MEDIUM findings
  (`repo-harness-compatibility-fixer` delegated agent)
- Iterate until zero CRITICAL/HIGH/MEDIUM findings achieved
- Report LOW findings without fixing them

### Pre-Release Validation (OCD Mode)

```
User: "Run repo harness compatibility quality gate workflow in ocd mode"
```

The orchestrator invokes agents with zero-tolerance criteria:

- Fix ALL findings (CRITICAL, HIGH, MEDIUM, LOW)
- Iterate until zero findings at all levels

### Targeted Single-Harness Check

```
User: "Run repo harness compatibility quality gate workflow in normal mode"
```

The orchestrator invokes agents and the checker focuses its `web-research-maker`
delegation on harnesses that have recent upstream activity, returning a lean audit
covering only CRITICAL and HIGH findings.

## Safety Features

**Infinite Loop Prevention**:

- `max-iterations` defaults to 7 — override with a higher value for more attempts
- Workflow terminates with `partial` if limit is reached
- Tracks iteration count for observability
- Escalation warning at iteration 5 if not converging

**Research Quality Safeguards**:

- Checker cites source URL and retrieval date for every upstream fact in the audit report
- Fixer re-validates each finding before applying (prevents acting on stale research)
- Out-of-scope findings are surfaced to the human rather than silently skipped

**False Positive Protection**:

- Fixer re-validates each finding before applying
- Progressive writing ensures audit history survives across iterations
- Checker logs whether research was reused or refreshed per harness

**Error Recovery**:

- Continues to verification even if some fixes fail
- Reports which fixes succeeded and which were flagged for human resolution
- Generates final report regardless of status

## Success Criteria (Gherkin)

```gherkin
Scenario: All harnesses compliant after one iteration
  Given the platform-binding catalog lists the currently supported harnesses
  And web-research-maker returns current upstream conventions for each harness
  When the repo-harness-compatibility-checker runs in strict mode
  Then the audit report should contain zero CRITICAL, HIGH, or MEDIUM findings
  And the workflow should proceed to confirmation re-check
  And on second consecutive zero-finding check the workflow should terminate with pass

Scenario: Drift detected and auto-fixed
  Given the platform-binding catalog entry for a harness is outdated
  When the repo-harness-compatibility-checker detects the drift
  And the repo-harness-compatibility-fixer applies the catalog update
  And the checker re-validates and finds zero threshold-level findings
  And the confirmation re-check also finds zero findings
  Then the workflow should terminate with pass
  And the corrected catalog entry should be present in docs/reference/platform-bindings.md

Scenario: Out-of-scope finding requires human resolution
  Given the checker detects a breaking harness change requiring a product decision
  When the fixer flags the finding as out-of-scope
  Then the workflow should terminate with partial
  And the audit report should describe the finding with full context for human review

Scenario: Max-iterations safety limit reached
  Given threshold-level findings persist across multiple fix iterations
  When the iteration count reaches max-iterations (default 7)
  Then the workflow should terminate with partial
  And the final audit report should list all remaining findings
```

## Notes

- **On-demand only**: This workflow does not run automatically on every push. Schedule it
  periodically or trigger it when upstream harness changes are announced.
- **Pre-push guard is separate**: `rhino-cli agents validate-bindings` (the pre-push parity
  guard) checks internal consistency deterministically and runs automatically. This workflow
  checks external conformance via web research and runs on-demand.
- **Idempotent**: Safe to run multiple times without breaking working state.
- **Observable**: Generates audit reports for every iteration in `generated-reports/`.
- **Bounded**: `max-iterations` prevents runaway execution.

## Principles Implemented/Respected

- PASS: **Explicit Over Implicit**: All steps, conditions, and termination criteria are
  explicit
- PASS: **Automation Over Manual**: Fully automated validation and fixing without human
  intervention (except for out-of-scope findings)
- PASS: **Simplicity Over Complexity**: Clear linear flow with loop control
- PASS: **Accessibility First**: Generates human-readable audit reports
- PASS: **Progressive Disclosure**: Can run with different mode levels
- PASS: **No Time Estimates**: Focus on quality outcomes, not duration
- PASS: **Root Cause Orientation**: Tracks upstream harness changes as the root cause of
  external drift rather than treating binding file content as inherently broken
